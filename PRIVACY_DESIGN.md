# Account-erasure implementation design

Status: implementation in progress; this document does not claim an available deletion workflow or completed privacy release gate. No actual account or installation is to be erased during development.

The verified user must reauthenticate and type an explicit whole-account confirmation. The client generates a request UUID and private 256-bit receipt before submission, so a lost acknowledgement can recover status after sessions are revoked. No receipt or password enters URLs, logs or process arguments. Public receipt status returns minimal progress only.

A separate, operator-initialized current privacy vault holds immutable HMAC-approved intents, a stable vault ID, externally pinned signing-key fingerprint and monotonic sequence. It stores a keyed owner fingerprint, workspace/request IDs and receipt hash, without email, name, password, project contents or the raw receipt. The render/ingestion roles receive neither this vault nor its signing key. Missing or damaged vaults fail closed; serving or restoring must never initialize an empty replacement automatically. Tombstones remain to prevent approved historical restoration from recreating an erased identity.

A reversible per-account mail-dispatch hold is prepared before the intent. No payload is removed at that stage. The private intent then commits before session revocation, permanent mail suppression/disposal or the studio barrier. Commit and recovery both acquire mail then vault: an abandoned hold may be withdrawn only after an authoritative absent-intent check under the mail mutex, and a later request cannot commit against that withdrawn hold. A crash after private approval keeps the durable preparation paused until verified activation. Every intermediate phase is resumable. Auth/session creation and mail callbacks deny an approved owner immediately. Cross-process mail suppression shares the queue mutex: pending messages can be discarded, captured sends finish or reach their existing bounded lease before finalization. An already accepted SMTP message cannot be recalled. New registrations with a different user ID remain possible after completion; legacy mail without an account ID needs separately scoped email-fingerprint suppression.

A transactional studio barrier hides/Trashes existing projects, cancels admitted exports/uploads and blocks new project/media/provider writes, including stale in-flight requests. Existing native leases and actual file accounting remain until verified teardown. A dedicated private worker verifies the signed approval and schedules bounded batches through the existing project deletion/reference-protection pipeline. It finalizes only after all projects, pending imports/provider calls/native leases/mail sends and indexed resources close; then it removes the account credentials/sessions, workspace-owned receipts/counters and relevant derived ownership records. Provider spend receipts must be detached from the erased workspace without releasing their shared settled/uncertain charges; account erasure must never become a way to reset the service spending budget. Unknown filesystem or ownership state remains blocked for operator review, without pretending it was erased.

Backups must declare the erasure capability and vault watermark. Production restoration requires the independently current vault, refuses a vault older than the snapshot, and reconciles approved users/workspaces in the restored copy before authentication or consumers start. Pending restored work remains hidden and resumable. A matching ID/signature and a snapshot lower watermark cannot prove that an operator-supplied journal is globally latest; the operator must preserve a current independent vault/anchor. A stale matching journal newer than an old snapshot is an explicit operational rollback risk, not a cryptographically solved guarantee.

Logical active-data cleanup is separate from physical SQLite/WAL disposal, filesystem snapshots, downloads, off-host backups and provider retention. Those controls need explicit retention/restore tooling and hosting acceptance before public release. Development uses synthetic account/media/mail fixtures; live SMTP/provider checks stay deferred.

Minimal studio tombstones retain opaque former owner/workspace/request IDs and the signed approval, without names, addresses, credentials or film content, to refuse stale producers recreating an erased workspace. Verification links must bind the account ID as well as the email: an old email-only token must not verify or automatically sign in a different account registered later with the same address. Previously queued unbound links require a new resend when this protocol is enabled.

### Authentication integration checkpoint

The candidate now registers the independent session-admission reader on real auth connections and requires the explicit pinned authority in production. Unit and browser harnesses initialize only their own synthetic authority. Existing approved sessions are filtered from real session reads before private Studio/API access, and signed-in auth mutations are rejected. Verification dispatch uses a per-request adapter copy whose lookup and update are pinned to the signed original ID, preventing an address-reuse race between asynchronous vendor steps. All five focused real-authentication/HTTP cases pass, including that race. This checkpoint does not expose deletion to users: studio orchestration, copied-backup reconciliation, worker cleanup and confirmation/recovery UX must land first.
